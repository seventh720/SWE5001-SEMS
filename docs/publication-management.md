# Unified editing and publication management

**Ended events:** once the current `endsAt` is at or before the server time, new detail, presentation and combined revision edits are rejected. Changing dates cannot reopen the event; create a new event, optionally from its template. UI controls follow the same rule. Existing durable operations retain their receipt-based recovery behavior.

Entering an editor hides the event list and other-event actions. Details, artwork, schedule, capacity and ticket types share a form; Save/Close sit below ticket settings. Only Registration information is locked after first publication. Published ticket names, quotas and registration windows remain editable; new ticket types can be added. Tickets used by a booking (including a cancelled booking) or pre-registration cannot be deleted. Existing ticket IDs, issued credentials, quantities and contact snapshots are preserved; historical order ticket-name snapshots remain unchanged.

Saving published changes automatically updates the public event once synchronization completes. There is no second publish step. Drafts stay private and paused events stay paused when edited. Initial publication still uses Publication preview with confirmation. Publication management contains Edit, public viewing (when published), Pause and Resume. Pausing hides public discovery and blocks new bookings/pre-registrations; it does not cancel or invalidate existing tickets. Resuming restores visibility subject to normal event and sales times.

The revision request adds optional `ticketConfiguration: {version, ticketTypes}` and `publicationStatus: PUBLISHED|PAUSED`. Existing ticket rows include their IDs; new rows omit IDs. Catalog stages the full desired state, marks UPDATING and sends the existing durable operation to Admission. Admission locks the sales row, validates ticket ownership/version, reserved counts, unique names, quotas and windows, then atomically applies tickets and sales metadata/status with its idempotent receipt. Catalog applies presentation/status only after acknowledgment. A business rejection rolls back Admission and restores Catalog's prior state; network interruptions are retried. First publication cannot be bypassed by the revision command.

The frontend sends explicit sales windows when editing dates; it does not silently shift them. Legacy revisions without ticketConfiguration retain the earlier automatic shift behavior. A first creation uses POST to obtain a private draft ID, followed by a combined revision; a failed second step retains that ID for retry instead of creating duplicate drafts.

Schema changes are owned by each service's Flyway migrations. Check data/state compatibility before rollback: binaries that do not understand PAUSED or CANCELLED cannot safely operate on those persisted states. Follow the [delivery guide](k3s-cd.md) and the [legacy upgrade guide](organization-upgrade.md) when applicable.

Run `scripts/editor-acceptance.py` only on a disposable stack. It includes previous acceptance suites and verifies atomic rejection, capacity/issued-place bounds, ticket version conflicts, ID/credential preservation, safe deletion, name swaps, pause/resume with outage recovery, first draft configuration and denial of stale first-publication retries while paused.

## Whole-event cancellation

An organization manager can cancel a PUBLISHED or PAUSED event with `POST /api/v1/organizer/events/{id}/cancel`, its current version and a nonblank reason (up to 500 characters). Publication management requires explicit confirmation. Complete any pending publication/revision first; cancellation is terminal, not a pause.

Catalog commits CANCELLING and the immutable operation before contacting Admission. Public discovery and new eligibility checks stop immediately. Admission takes the event advisory lock followed by the sales row lock, atomically marks sales CANCELLED, cancels every CONFIRMED booking, invalidates VALID tickets, releases reservations and inserts private notifications plus an idempotency receipt. CHECKED_IN tickets, timestamps and staff attribution remain as history. Confirmed tickets and available places become zero; historical attendance remains visible without an active progress bar. Saved registrations become CLOSED. Existing attendee cancellations are preserved.

Booking, attendee cancellation, pre-registration and check-in all serialize on the same sales row. Work that wins the lock before whole-event cancellation is included in its final result; work after it cannot create valid tickets or check in. A stale remote activation or revision cannot revive cancelled sales. Replaying a completed revision receipt is a no-op. Late event-update notifications are suppressed after local cancellation.

Catalog marks CANCELLED only after acknowledgment. While Admission is unavailable, CANCELLING remains durable and ticket invalidation is still pending; the worker retries every five seconds, including after restart, without requiring a fresh user session. Transport errors or conflicts never restore publication. If Admission commits and the response is lost, the matching receipt makes replay safe. Completed Catalog requests return the existing result even when Admission is offline. Reusing a cancellation with a different reason/version is rejected.

Do not roll back to older binaries while cancellation operations or terminal states exist; restoring an older binary alone is not a database rollback. For a persistent pending operation, check service health/connectivity and the matching operation in `catalog.event_cancellations` / `admission.event_cancellation_receipts`; repair the underlying service failure and let recovery retry. Do not delete receipts or manually reopen cancelled sales.

`python3 scripts/event-cancellation-acceptance.py` is wired into CI and must run only on a disposable stack. It tests 100 booking requests competing with check-in, attendee cancellation and duplicate whole-event cancellation; a late transaction fault; Admission outage; Catalog restart; and a lost acknowledgment. This is local consistency evidence, not a measured cloud recovery SLA.
