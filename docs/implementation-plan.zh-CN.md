# 平台实施计划

## 服务职责

Identity 管理账号、认证与角色；Event Catalog 管理活动、所有权、发布与发现；Admission 管理票种、库存、订单、票券、工作人员分配与签到。Web 应用通过网关调用版本化 API。

每服务拥有独立数据库 schema、凭据和迁移。跨服务仅通过认证的 HTTP API 协作，不共享实体、Repository、外键或跨 schema 查询。订单、库存与票券保留在 Admission 本地事务中。

## 平台场景

社团发布 seminar，培训机构发布 workshop；二者使用同一目录、库存、预订、票券和签到能力，服务端按 owner 隔离管理权限。第三个组织者注册并由管理员授权后即可发布，无需修改代码或重新部署。记录配置步骤、用时和能力映射。

## 实施顺序

1. **契约与基础设施**：三份 OpenAPI、独立 schema/凭据、JWT 验证、网关业务路由；验证跨库访问被拒绝。
2. **身份与活动**：账号注册、登录、角色管理、所有权检查、活动草稿和目录；发布必须在 Admission 激活协议完成后开放。
3. **票务闭环**：销售窗口、免费票种、幂等预订、唯一票凭证、取消、工作人员分配、一次签到与统计。
4. **跨服务与应用**：持久化发布/取消操作，处理超时和重启恢复；完成 Web 页面与多组织者演示。
5. **部署与证据**：云端独立部署及回滚，安全扫描与质量门禁，25/50/100 VU、1/2副本和故障恢复实验。

## 关键实现要求

Admission 使用数据库锁、唯一幂等键和条件状态变更保护并发正确性。HTTP 校验不能代替数据库锁，JVM 锁不能协调多个副本。发布和取消采用持久化状态、幂等命令与恢复任务，详见架构决策。

首版仅草稿可修改时间、容量和票种配置。核心仅免费票；付费、通知、头像和预约预填不进入首轮范围。二维码出票与工作人员签到须实现完整业务能力。

## 工作划分与交付

建议按 Identity/交付、Catalog/协议、Admission/一致性、Web/端到端划分工作面，负责人由团队确认。Admission 工作量最大，可由其他成员协作出票和签到。预算为40 person-days，记录实际贡献和投入。
