# 技术改进计划

整理日期：2026-10-23。最近发布与已完成验证见[发布状态](progress.md)，当前规则见[业务说明](functional-guide.md)。本文只记录后续工程工作；实验方案和目标不表示已经完成验证。

## 性能与容量

- 定位内部活动详情读取的长尾超时。现有结果确认发生了 4 次内部 504，但不足以确定唯一根因。结合请求日志、连接获取/占用计时、SQL 和主机资源采样分析，保留现有判定阈值。
- 在独立测试环境执行预热后的 100 VU 十分钟稳态，按操作记录吞吐、p95、意外错误和业务拒绝。待验证目标为 p95 < 3 秒、意外错误率 < 1%；不得用短时阶梯替代稳态。
- 分别比较 Catalog 和 Admission 的 1/2 副本，固定其他服务、每副本资源、数据和负载，至少进行交错重复。当前没有独立云端扩容收益结论。
- 评估大规模目录的组织 ID 聚合成本，以及同步 Identity 调用、共享数据库与热点 sales 行锁的影响。

最新已完成实验使用 50 场普通活动和 1000 个账号；250 VU 读取通过，混合负载因内部 504 未通过服务端门禁，500/1000 VU 未执行。后续对照方案中的 100 活动数据集尚不能作为已有结果。完整方法见[实验说明](performance-and-availability.md)。

## 故障恢复与交付

- 在持续业务负载下分别停止一个 Catalog/Admission 副本，记录故障到恢复的时间、流量分布、订单和库存核对。待验证目标为 60 秒内恢复；已有本地恢复检查未测得该云端结论。
- 演练单服务兼容镜像回滚和数据库备份恢复。明确镜像回退不撤销 Flyway 迁移，分别保存两类操作的结果。
- 安排定期异地备份，检查保留策略和恢复可用性。目前备份与业务数据库仍在同一台主机上。

## 可观察性与接口验证

- 在已有网关日志、readiness、请求/operation ID、资源和数据库快照上补持续监控与告警。
- 增加自动 OpenAPI 请求/响应符合性检查；现有 API 验收不等同于完整契约符合性门禁。
- 单独采集关键真实数据库/API 验收的覆盖范围，明确 SQL、事务、重试和恢复路径，不将单元覆盖率套用到集成验收。

## 维护与界面回归

- 修改相关文件时改善过度压缩的 Java/TSX 排版，按实际复杂度整理治理和核销逻辑。
- 将验收脚本中隐式的 `runpy` 调用链逐步改为明确的公共 helper。
- 按实际使用需求补充邀请历史分页、复杂编辑器错误分支、真实浏览器键盘/缩放/滚动和设备权限场景。

## 设计边界与验收方式

当前部署是单台 Lightsail、单个 PostgreSQL 实例和三个服务。schema、账号、迁移和镜像各自独立，但宿主机、数据库和入口仍有单点；增加容器不能证明主机级高可用或自动扩容。Admission 将库存、订单、票券和核销保留在同一服务，以本地事务保护一致性，暂无继续拆分的工程依据。

每项验证保留 commit、镜像 digest、配置、数据规模、时间段、负载模型、原始结果与数据库核对。功能正确性、容量、扩容收益和恢复时间分别判断。失败结果也保留。实验与故障注入只在隔离环境进行，不改变共享业务数据。现有验证映射见[验收矩阵](acceptance-matrix.md)。
