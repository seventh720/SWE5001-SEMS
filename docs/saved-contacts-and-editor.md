# Saved contacts, usernames and event editor

Identity V3 migrates the existing reusable profile to a named **My details** contact (retaining name, email, phone and passport). The reusable Student ID column is removed. Existing event-specific registration requirements, bookings and pre-registrations are unchanged; an event that requests Student ID still requires manual entry. This is removal from saved contacts, not removal of historical booking information.

Authenticated users manage multiple named contacts through `/api/v1/profile/contacts`. Each contact has an opaque ID and version; updates and deletes enforce owner and version, returning 404 for other owners and 409 for stale versions. Responses prohibit caching. The old `/api/v1/profile` endpoints remain deprecated compatibility operations on the default contact only; Student ID writes are ignored and reads return null.

The profile page groups its privacy notice and optional contact information under **Saved registration details**. Users add, edit and delete contacts individually. Registration first opens a named contact selector, then applies the selected contact's requested fields for review. Missing fields are cleared to avoid mixing people, Student ID and the event-specific answer must be entered manually, and account email never changes. An order still has one booking contact for all places; per-ticket attendee assignment is a separate feature. Changes to saved contacts never alter submitted snapshots.

Usernames can be checked and changed from My profile. The same normalization and policy apply to signup and renaming: 3–50 ASCII letters, digits, dot, underscore or hyphen, at least one alphanumeric character, stored lowercase. Exact system names `admin`, `administrator`, `support`, `system`, `root`, `sems` are reserved. The availability check is advisory; a database unique constraint resolves simultaneous requests. User ID, email login, roles, tickets and contacts stay attached to the account. No third-party multilingual profanity detection or automatic moderation is implemented; introduce an agreed moderation policy before adding it.

Event details and ticket settings share one editor and one save operation. Published ticket types remain editable while registration information stays fixed. Drafts use Publication preview; previously published events use Publication management with explicit pause/resume. See [publication management](publication-management.md).

Deploy Identity with migration V3 before deploying the new web bundle. The Student ID column removal is intentionally not reversible without a prior database backup; rolling back to the old Identity binary is not supported after migration. No external moderation service or notification is required.

Validation: `scripts/contacts-acceptance.py` includes the prior schedule/booking/publication regressions plus contact ownership, stale versions, deletion, no Student ID retention, username validation, normalization, login continuity and concurrent duplicate rejection. UI tests cover choosing a contact, profile editing, session name refresh and the inline ticket/publication separation.
