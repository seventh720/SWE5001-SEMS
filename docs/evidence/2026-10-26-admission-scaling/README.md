## 实测判断

本轮本地对照中，双副本使分散组吞吐增加 55.5%，热门组增加 26.1%。分散组订票 p95 从 194.66 ms 降至 124.28 ms；热门组从 155.76 ms 到 155.08 ms，基本不变。

扩容后 PostgreSQL 平均 CPU 分别达到 0.990 / 0.973 核，其 CPU limit 固定为 1 核；发生 CPU 限流的周期比例分别为 95.8% / 49.5%。热门双副本的 Admission 合计只使用约 1.564 核，两个 Pod 的 CPU 限流周期比例约为 1.3% / 3.4%，应用 CPU 已有余量。

热门组的 Admission 会话锁等待采样占比从 77.6% 增至 85.6%。一次现场 SQL 分类采样中，14 个连接正在等待 `sales` 活动行的 `FOR UPDATE`。这些观察支持将后续工作转向数据库 CPU 配额及热点活动锁，而不是预期继续增加 Admission 副本就能线性提高吞吐。可以先在隔离测试环境单独提高 PostgreSQL CPU 配额复测，区分 CPU 上限与锁争用的影响；本轮没有调整数据库配额或库存锁实现。

数据库 CPU 配额的后续对照已完成，见[独立 CPU 实测](../2026-10-26-postgres-cpu/README.md)。后续实验用于检验这里观察到的配额限制是否转化为端到端收益，未修改本报告原始结果。
