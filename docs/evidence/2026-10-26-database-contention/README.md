# 数据库热点压测 · 2026-10-26

新加坡时间 2026-10-25 23:55:18 至 2026-10-26 00:34:07，在本机 `kind-sems-local/sems-benchmark` 完成两组有效对照。固定同一数据库快照、50 个测试账号、10 个公开活动、每活动 1,000,000 库存；只改变请求集中在首个活动或分散到十个活动。每组 50 VU、60 秒预热、600 秒测量，一次有效样本，无 think time。每次迭代订一张票后读取回执，包含两次 HTTP 请求。

五个应用均固定 1 副本。三个后端各 limit 1 CPU / 768MiB，PostgreSQL limit 1 CPU / 512MiB；k6 limit 1 CPU / 256MiB。Docker VM 为 10 CPU / 7.75 GiB，既有容器共同使用该 VM，经 port-forward 访问 Gateway。应用镜像 ID 与[此前本地预检](../2026-10-25-kubernetes-scaling-preflight/README.md)逐项匹配，构建源为 `f33bf83168a44841895d074e917f01ff6ed5d70b`；实际镜像、资源、JAR 哈希、采样统计和原始工具哈希见 [results.json](results.json)。本轮仅修改压测工具，未修改业务实现。

## 判断

- 热门组确实在活动行上争用：分类现场采样中，7 个连接等待 `sales` 的 `SELECT … FOR UPDATE`；分散组显著减少了锁等待。
- 两组 Admission 的 CPU 均接近 1 核上限，且频繁发生 cgroup CPU 限流。当前存在明确的应用 CPU 配额限制；PostgreSQL 的平均 CPU 低于其 1 核上限。下一步应固定数据与负载，比较 Admission 的 CPU 配额或副本数，再决定是否细化活动锁。
- 本轮分散请求后吞吐没有提高。两组各一次有效样本，不能把锁等待降低直接解释为吞吐收益，也不能证明数据库需要加 CPU/内存。`track_io_timing=off`，读写计时为零不构成无 I/O 瓶颈的证据。
- PostgreSQL `max_connections=100`，采样中三服务连接合计最多 30，Admission 每轮保持 10 个连接；本轮未出现连接上限耗尽或新增死锁。没有调整连接池或数据库参数。

Gateway 日志通过事后读取当前日志获取，留存片段不足以覆盖完整窗口。因此本轮客户端阈值通过，完整服务端日志门槛未验证；片段里的零重试不能解释为全窗口零内部错误。各轮 Admission access log、k6 原始样本与库存审计分别保留。

本轮只覆盖订票与回执，不覆盖订单列表、目录搜索、HPA、跨节点扩容或 AWS 容量。对照使用同一批活动，但有效执行顺序为分散组、热门组；每轮重启三个测试后端并恢复同一数据库快照，缓存和运行顺序仍是限制。

## 数据一致性与恢复

热门组结束时，新数据集确认订单数量、预留库存、有效票数均为 263,971；分散组均为 215,087，均包含预热。十个票种逐项满足 `reserved = confirmed quantities = active tickets`，没有超配额；这些数值不能直接与稳态成功订单数相减判断丢单。

两个有效轮次都没有 Pod 重启、镜像变化、资源保护停止或采样中断，最大资源采样间隔分别为 5.219 / 5.213 秒。结束后保留最终测试库快照，还原造数前备份；27 张表的全部 COPY 数据逐表排序后计算 SHA256，与原备份一致。五个应用恢复各 1 个 Ready 副本，原 PVC UID 未变。恢复后首次健康检查返回 502，稍后复核 Gateway 和三个后端均为 200；这发生在压测结束后的恢复阶段。生产与其他本地业务环境未被本次脚本修改，没有创建 AWS 资源。

## 被排除的第一轮

首次热门组遇到 macOS 自动 Idle Sleep（00:05:27–00:08:10），相邻资源采样空档为 166.328 秒。其 k6 阈值和库存核对通过，但不满足连续十分钟测量，因此排除出上表，并以同一快照补跑。异常样本与[summary](sleep-interrupted-summary.json)保留，未把它改写成稳态通过。后续使用临时 `caffeinate -i` 防止闲置睡眠；工具增加采样间隔超过 15 秒或时钟倒退时停止的检查及回归测试。
