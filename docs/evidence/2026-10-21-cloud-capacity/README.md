## 方法与结果

共享新加坡 Lightsail：2 vCPU、3832 MiB，同时运行 SWE5006。三个 Java 服务各一个副本、每个上限 768 MiB，数据库 512 MiB，网关/前端各 96 MiB，共享 Caddy 256 MiB。本轮使用原部署配置。

独立本机 Docker k6 1.3.0 限制 4 CPU/2 GiB，访问公开 HTTPS。创建 1000 个账号、100 场普通活动和独立的 100 票库存竞争活动；注册与低速登录准备不计入成绩。普通活动十页返回恰好 100 个不同 ID，与造数清单一致。

参考 SWE5006：每轮依次读取活动分页、活动详情、本人资料及本人订单，再等待 1 秒；混合场景每五轮增加订票→回执→取消，每 VU 最多 60 次。每档爬升 30 秒，低档保持 30 秒，500/1000 档计划各保持 180 秒，档间恢复 10 秒。整体和逐接口 p95＜3 秒、真实错误率＜1%，全部状态/内容检查通过；失败即停止后续阶段。两套系统六项健康探针及内存、重启/OOM、监控断线保护持续运行。复现见[实验说明](../../performance-and-availability.md)。

读取/混合的 1 VU 预检通过。读取失败后，确认系统健康，刷新前 250 个账号的 JWT，单独运行上限 250 VU 的混合阶梯。两轮均保留 STOPPED 判定。读取 1000、混合 500/1000、热门活动库存竞争均未执行。

请求总数包含爬升与收尾，保持期指标按请求开始时间标记并排除这些阶段；没有保持期样本时 p95 为 null。原读取控制器曾将 k6 空指标的 0 直接写入结果，汇总按样本数纠正，私有原文件保留。汇总还保留逐接口请求数及延迟，避免整体指标掩盖慢接口。

## 瓶颈与修正

读取窗口出现 65 条 `worker_connections are not enough`、Caddy 140 次 502；混合窗口出现 60 条同类告警、185 次 502，另有网关 500/503/504。代理和 k6 的计数受采集窗口、在途取消及代理重试影响，不能逐条等同。连接额度是已命中的瓶颈，是否还有 CPU 或跨服务调用瓶颈需复测。

参考 SWE5006，候选网关加入自动 worker、每 worker 4096 连接/8192 文件额度、各上游 32 个空闲复用连接，以及 HTTP/1.1 和清空 Connection 头。连接额度同时覆盖客户端与上游，keepalive 仅限制空闲池；参见 [Nginx 连接额度](https://nginx.org/en/docs/ngx_core_module.html#worker_connections)与[上游复用](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)。

本地配置、健康及组织管理 API 回归通过；1635 次订票与同键重放/实时回执通过 Catalog 冷重启回归，全副本停机仍有界失败，恢复后幂等及库存审计通过。候选尚未部署云端；下一步部署后重跑阶梯，不能将本轮结果写成修正后成绩。

## 资源与清理

读取/混合分别采集 66/45 个样本，最低可用内存约 1361/1340 MiB，数据库连接峰值 31/32，锁等待者采样均为零。两轮健康探针全部成功，最长约 1.94 秒；容器身份、重启计数和 OOM 状态无变化，健康保护未触发。load1 峰值 34.89/23.54，仅记录。生成器 CPU 峰值 48.90%/45.05%，内存峰值为 2 GiB 限额的 9.03%/6.62%。停测由业务错误阈值触发。

101 场活动的库存占用＝确认数量＝有效票数，且不超过 quota。共 1318 笔单票订单，1291 笔已取消、27 笔仍有效，与 27 张有效票一致。停测中断了部分取消循环，随后通过产品取消活动全部处理；没有超卖，热门活动竞争仍待验证。

产品 API 取消活动、关闭组织和撤销组织者角色后，服务器保存并校验备份，精确 ID 事务完成回滚预演及删除：1000 个账号、1 个组织、101 场活动、1318 笔订单/票及本轮关联记录。新数据库会话确认原有业务 24 张表的计数和内容指纹不变，两套系统六项健康检查正常。备份只留服务器，本地密码和令牌已移除。

本轮数据量和跨服务模型不同于 SWE5006，也不同于原 0.1 秒思考时间的扩容脚本。结果只适用于指定短时负载；100 VU 十分钟稳态、1→2 副本重复对照和云端故障恢复仍需分别完成。
