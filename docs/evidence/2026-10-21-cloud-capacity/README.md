## Catalog 延迟定位（同版本，独立诊断）

同日对 `054690b` 新建 1 个隔离账号和 100 场活动，运行 90 秒只读诊断：30 秒升至 250 VU、20 秒升至 500、保持 30 秒、10 秒降至零。每轮仍读取列表、详情、本人资料、空订单并等待 1 秒；所有 VU 共用一个真实 JWT。健康/内存保护沿用容量实验，另采集三次 Catalog/Identity 线程栈、主机 CPU、数据库等待与直接访问容器的内部只读探针。此模型和线程采样会影响时延，**不作为新的多账号容量成绩**；29,413 次状态/内容检查均通过，但列表全诊断 p95 3.96 秒，k6 保留失败退出码 99。

**主要观察是 Catalog 数据库连接获取排队，同时共享两个 CPU 已饱和。** 三次线程栈均有 200 个 Catalog 请求线程，其中 153/160/170 个停在 Hikari `ConcurrentBag.borrow` / `getConnection`；等待者中列表分别为 106/108/135 个，详情为 47/52/35 个。数据库侧 Catalog 始终观察到 10 个连接，与当前未显式设置池大小和 [Hikari 默认值](https://github.com/brettwooldridge/HikariCP#frequently-used)一致。少量已取得连接的线程在 JDBC 查询/提交，不能把等待连接等同于数据库正在执行慢 SQL，也不能据此直接决定扩池。

高负载区间九个 CPU 样本的平均空闲仅 0.26%，I/O wait、steal 均为零；Catalog cgroup 无 CPU quota 限流。六类代表 SQL 根据仓库条件重建，通过只读事务执行 `EXPLAIN (ANALYZE, BUFFERS)`：低负载执行约 0.040–0.510 ms，高负载约 0.039–2.387 ms；高负载规划时间最高 27.867 ms。数据库活动采样未见锁等待，活动查询最大年龄约 76 ms。这些是有限的直接 SQL 样本，不含应用排队、JDBC 往返及 ORM 映射，不能视作全部真实 SQL 的延迟分布。当前 100 活动数据量下，证据不支持优先通过加索引处理秒级延迟。[EXPLAIN 的计时范围](https://www.postgresql.org/docs/16/using-explain.html)与请求耗时不同。

容器直连探针排除了公开 HTTPS 链路，内部详情/发布状态读取最长约 2.599/2.485 秒，同期直接 Identity 批量组织查询最长 0.337 秒。内部详情接口本身不调用 Identity，也发生延迟，说明三类查询共同受到 Catalog 资源排队影响。内部网关的 2 秒读预算会先于公开请求的 3 秒目标耗尽，与容量复测的内部 504、订票 503 传播链一致；不能只通过放宽超时消除失败。

调用链还存在可以缩短连接占用的具体改动点：

- [公开列表/详情](../../../services/event-catalog/src/main/java/com/sems/platform/catalog/PublicEventController.java)每次实时查询组织状态；列表通常还需组织 ID、分页实体、总数三类 Catalog 查询。保留停用组织立即不可见和先过滤后分页的口径。
- [发布状态读取](../../../services/event-catalog/src/main/java/com/sems/platform/catalog/PublicationState.java)在 `@Transactional(readOnly=true)` 内读取活动后同步调用 Identity。把只读快照读取与远程校验拆开，可以避免等待网络时占用数据库事务；这尚未修改，也尚未量化其收益。
- [内部批量详情](../../../services/event-catalog/src/main/java/com/sems/platform/catalog/EventDetailsController.java)目前加载完整 Event 后取六个字段，可改为只查询所需字段，减少映射和连接占用；同样需要对照验证，不能预先宣称已提速。

下一步先补连接获取/占用和 Identity 调用分段计时，完成上述小范围读取改动；在固定资源下对照当前池与少量候选池大小，例如 10/16/20，记录等待、吞吐、CPU 和逐接口 p95，选择有实测收益的配置。CPU 已饱和，不能仅增大线程/连接数，或直接在同一双核主机增加副本来保证收益。若优化后仍受 CPU 限制，再在独立云端环境对照 CPU 预算及 Catalog 1→2 副本。复测先验证读取 500 VU 三分钟和混合 250 VU 全部状态检查，再逐级推进至 1000。
