## 环境与方法

- 两节点均为 `t3.medium`，各 2 vCPU / 4 GiB；控制平面、应用、监控和数据库共享节点。
- PostgreSQL 17.11 为单 Pod/PVC，限额 1 CPU / 768 MiB；后端每副本请求 250m / 512 MiB，限额 1 CPU / 768 MiB。
- 数据集为 1000 个账号、100 个已发布活动，每活动 1000000 票额。测试使用原 PostgreSQL 内的临时逻辑数据库，每轮恢复相同快照，原业务库 `sems` 保留。
- 本机 Docker 中的 k6 1.3.0 经公网 HTTPS 发压，限额 2 CPU / 1 GiB。客户端样本、summary、网关计数、逐副本流量及 SQL 库存分别核对。
- 性能脚本版本 `ef7c6c9b3fc37a55dd2b25a317bb40650be25292`；后续恢复脚本版本 `2083b0fae6721ae0e61b4e8c3dc5e9619c329576`。离线记录保留各阶段实际源文件哈希。

## 十分钟混合负载

100 VU，60 秒爬升、600 秒稳态，思考时间 1 秒，三个后端均为双副本。持续执行目录、详情、本人资料和订单读取，每五次迭代执行订票、回执和取消。

稳态 178959 次 HTTP 请求，0 意外客户端错误，总体 p95 约 338 ms，最慢操作订票 p95 约 525 ms。十个分钟窗口均有成功订票；网关测量计数、服务端门槛及 SQL 库存审计通过，六个业务副本均收到成功业务流量。结果支持本环境的 100 VU 十分钟目标，不代表最大容量。
