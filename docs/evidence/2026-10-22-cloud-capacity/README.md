## 测量前置问题处理

首次1 VU读取预检的20次请求全部成功，但保持期样本为零，原计数门槛判失败；随后在250目标档前停止了混合预热。该次记录不记为容量通过，也不作为250 VU容量失败，原始失败与中断摘要保留在结构化汇总中。

本机无HTTP探针随后观察到30–34秒的五次正常保持期迭代；正式执行期间使用 `caffeinate -i` 防止负载机空闲睡眠，未修改业务脚本、持续时间或评分。尚未确认初次计时异常的唯一根因。服务器本机备份、精确ID回滚预演后，仅重置预热产生的688笔临时订单及票券，保留1000账号和50活动；新会话确认原业务24表指纹不变，库存及订单历史恢复为零后再执行本页正式结果。异常记录和清理SQL仍留在本轮私有目录。

## 剩余504与收尾决定

本轮4次504均在内部只读批量详情接口。内部网关的读取超时为2秒；Admission已对该类详情失败降级，保留订单和票券访问，并由UI提示最新活动信息不可用。因此本轮公开请求全部成功，仍不能将内部零错误门槛记为通过。

当前详情查询已采用按主键、六字段的参数化JDBC读取。现有日志还不能区分剩余尾延迟来自请求排队、连接获取、SQL还是共享主机调度，没有已验证且无需复测即可消除504的小修。延长超时可能减少网关504，但会增加等待时间，不能作为容量提升证明；减少同步详情查询或隔离资源留待pre后定位和验证。

本轮作为pre前最后一次容量实验，冻结业务代码和配置，不再追加调参/压测。按最新清理要求移除旧100场活动对照摘要，只保留本轮50场活动结果、测量前置异常、清理审计及业务验收材料；不改写Git历史。

## 模型与资源

通过真实API新建1000账号与50场普通活动。5页返回50个不同ID，与清单一致。注册/登录使用两个线程、全局起始间隔至少0.3秒；密码哈希与认证限流保留，准备请求不计入压测。每次独立suite检查真实JWT至少还有20分钟有效期，不使用伪造或共用JWT替代不同账号。

每轮读取活动分页、详情、本人资料和本人订单，再等待1秒；混合场景每五轮增加订票→回执→取消，每VU最多60次写入。读取250开始前没有订单历史；混合轮逐步增加取消订单，若执行后续读取轮则继承该历史，不重置数据库，不能把档位差异解释为纯VU的因果影响。每轮后的库存审计单独保存。

250档的每种模式先1 VU预检、50/100 VU各保持30秒预热；目标爬升30秒、保持60秒。500/1000目标分别爬升30秒、保持180秒。按读取/混合配对过关后升级；同档另一模式只有在共享健康恢复、容器运行身份未变时才独立运行，健康保护触发则停止后续负载。执行器只调整分档编排、250保持时长及服务端门槛，`cloud-capacity.js`业务模型与原评分阈值未改。

独立本机Docker k6 1.3.0（4 CPU/2 GiB）访问HTTPS。被测为新加坡共享Lightsail（2 vCPU、3832 MiB），SWE5006同时运行；三个Java服务各一个副本/768 MiB，PostgreSQL512 MiB、网关/Web各96 MiB、Caddy256 MiB，Catalog池10。六项健康、容器CPU/内存、退出/重启/OOM、可用内存及DB连接/锁等待均由原健康保护采样；详细边界见[实验方法](../../performance-and-availability.md)。
