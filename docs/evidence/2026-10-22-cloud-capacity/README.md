## 模型与资源

通过真实API新建1000账号、100场普通活动及1场未用于本次争抢测试的独立100票活动。11页返回101个不同ID，与清单一致。注册/登录使用两个线程、全局起始间隔至少0.3秒；密码哈希与认证限流保留，准备请求不计入压测。每次独立suite检查真实JWT至少还有20分钟有效期，不使用伪造或共用JWT替代不同账号。

每轮读取活动分页、详情、本人资料和本人订单，再等待1秒；混合场景每五轮增加订票→回执→取消，每VU最多60次写入。读取250开始前没有订单历史；混合轮逐步增加取消订单，后续读取轮继承该历史，不重置数据库，不能把档位差异解释为纯VU的因果影响。每轮后的库存审计单独保存。

250档的每种模式先1 VU预检、50/100 VU各保持30秒预热；目标爬升30秒、保持60秒。500/1000目标分别爬升30秒、保持180秒。按读取/混合配对过关后升级；同档另一模式只有在共享健康恢复、容器运行身份未变时才独立运行，健康保护触发则停止后续负载。执行器只调整分档编排、250保持时长及服务端门槛，`cloud-capacity.js`业务模型与原评分阈值未改。

独立本机Docker k6 1.3.0（4 CPU/2 GiB）访问HTTPS。被测为新加坡共享Lightsail（2 vCPU、3832 MiB），SWE5006同时运行；三个Java服务各一个副本/768 MiB，PostgreSQL512 MiB、网关/Web各96 MiB、Caddy256 MiB，Catalog池10。六项健康、容器CPU/内存、退出/重启/OOM、可用内存及DB连接/锁等待均由原健康保护采样；详细边界见[实验方法](../../performance-and-availability.md)。

## 一致性与清理

每轮审计要求库存占用＝确认数量＝有效票数且不超quota。完成产品功能取消活动、关闭组织和撤销权限后，101场活动库存与有效票为零，全部2171笔订单/票已取消。服务器本机备份校验、精确ID事务回滚预演及正式清理通过：1000账号、1组织、101活动、2171订单/票及关联记录全部删除；新会话确认原业务24表指纹不变、六项健康正常。未下载完整数据库备份。临时密码/JWT已移除；原始指标、严格ID清理SQL和本版执行器仅保留于Git忽略目录 `.performance/cloud-20261022-jdbc-release/`。

## 证据边界

这是本版在指定共享主机、顺序增长历史、1秒思考模型下的一轮容量验证，不是交错重复的版本/参数对照。短时阶梯不替代100 VU十分钟稳态、独立单服务1/2副本收益、云端故障恢复或兼容回滚，不证明自动扩容或主机级HA。库存争抢未在本次执行；其业务并发正确性由现有API验收另行覆盖。未测量Lightsail突发额度历史，不仅凭CPU采样推断其影响。
