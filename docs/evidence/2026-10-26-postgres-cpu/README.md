# PostgreSQL CPU 配额对照 · 2026-10-26

新加坡时间 2026-10-26 03:04:16 至 2026-10-26 03:52:44，在本机 `kind-sems-local/sems-benchmark` 比较 PostgreSQL CPU limit 1→2 核。Admission 固定两个副本，其余四个应用各一个副本；每个场景各一次单/双核有效样本，共四轮。每轮 50 VU、60 秒预热、600 秒测量，无 think time，每次迭代订一张票后读取回执。

固定同一初始数据库快照、50 个测试账号、10 个活动、每活动 1,000,000 库存。数据库内存 limit 保持 512MiB，request 保持 100m CPU / 128MiB；三个后端单副本仍为 1 CPU / 768MiB，Admission 每副本连接池 10，总池容量 20，k6 固定 1 CPU / 256MiB。

每轮先停止三个测试后端，以轮次 annotation 触发 PostgreSQL 重启，等待 StatefulSet rollout 与 Ready，核对实际 Pod CPU limit，再恢复同一快照并启动应用。两种配额均经过数据库重启，PVC 不变。应用镜像与此前本地预检一致，构建源 `f33bf83168a44841895d074e917f01ff6ed5d70b`；四轮 PostgreSQL 与应用 image ID 均核对一致，未修改业务代码或库存锁。详情见 [results.json](results.json)。

## 实测判断

分散组吞吐从 559.97 到 550.30 单/秒（-1.7%），基本持平；订票 p95 从 122.89 到 153.51 ms。每种条件只有一次样本，不能将这些差异直接解释为加核造成性能退化。热门组吞吐从 433.32 到 475.22 单/秒（+9.7%），订票 p95 从 143.70 到 133.61 ms，本轮有小幅改善，需要交错重复确认稳定性。

数据库 CPU 配额确实生效：分散组 PostgreSQL 的 CPU 限流周期比例从 77.5% 降至约 0.2%，但端到端吞吐没有提高。与此同时，两个 Admission Pod 的限流周期比例增至约 87.7% / 67.5%，Catalog 约为 22.5%。数据库 2 核条件下的平均 CPU 使用仅约 1.057 核，不能依据原先数据库触及配额就推断加核必然提高整体吞吐。

热门组数据库 2 核时平均使用约 0.995 核，Admission 合计约 1.608 核，配额均有余量；Admission 会话锁等待采样占比仍约 84.0%。一次现场分类采样中，14 个连接正在等待 `sales` 活动行的 `FOR UPDATE`，另有一个会话处于 `WalSync` 等待。额外 CPU 没有消除热点事务的串行化；现有采样不能进一步量化锁持有、应用处理与提交 I/O 各自的耗时。

后续应优先定位 Admission / Catalog 的 CPU 热点，以及订票事务内各 SQL、持锁区间和提交阶段的耗时，再选择减少重复读取、减少数据库往返或缩短持锁时间的改动。本轮结果不支持把数据库继续加核作为主要提速方案；需要做资源决策时，应先完成多次交错重复及独立云端验证。

负载发生器各轮平均 CPU 约 43%–55%（100% 为其 1 核配额），最大采样约 79.6%，内存最大采样约为 256MiB 配额的 71.2%，没有负载容器 OOM 或持续满配额的迹象。

## 范围与复现

这是单节点 kind、本地共享 Docker VM（10 CPU / 7.75 GiB）上的单轮配额对照，经 port-forward 进入 Gateway。未做三次交错重复或云端容量验证。每轮初始快照相同，但预热会写入订单，测量开始时的订单量会随预热吞吐不同。每轮重启数据库也使流程不同于此前 Admission 副本对照，本报告只使用本轮单/双核配对。

首次入口预检在 Gateway rollout 完成前选中旧 Ready Pod，日志文件缺失，未开始负载；原库与配置已恢复。补上 Deployment rollout 等待后，入口预检通过，再执行本报告四轮；失败预检记录保留于本机。

复现参数为 `--modes booking --users 50 --events 10 --quota 1000000 --vus 50 --replica-counts 2 --postgres-cpu-limits 1 2 --distributions spread hot --think-seconds 0 --warmup 60 --duration 600 --repeats 1`，详见[实验指南](../../kubernetes-scaling-experiment.md#数据库-cpu-对照)。macOS 使用 `caffeinate -i` 阻止闲置睡眠。
